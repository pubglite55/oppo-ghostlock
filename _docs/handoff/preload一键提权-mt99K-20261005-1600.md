## 二、KernelSU 未 Live —— 三条路线全部实测判定

1. **`ksud late-load`：模块不在 ksud 里。** 设备上的 ksud = 官方 v3.3.0 standalone
   （6,286,568 B，与 release 资产同尺寸），它从**已安装的 manager APK** 取内嵌模块；本机没装
   `me.weishu.kernelsu` ⇒ 打印什么都**没有**、`rc=0`（不是被拦、不是崩溃）。
2. **`ksud insmod /proc/self/fd/<ko_fd>`：模块读到了，但死在 kallsyms。** fd 路径有效（报错信息里
   打印出真实路径 `/data/local/tmp/KernelSU.ko`），失败于
   `Cannot parse kallsyms / Operation not permitted (os error 1)`——`/proc/kallsyms` 需要
   `CAP_SYSLOG(bit34)`，本发 caps 没有。
3. **`finit_module(ko_fd, "", 3)`：唯一可行路线。** flags 3 = IGNORE_MODVERSIONS|IGNORE_VERMAGIC，
   不需要 kallsyms、不需要 manager APK，唯一门槛是 `CAP_SYS_MODULE(bit16)`。依据：设备 KO 是官方
   `lkm-aarch64-android12-5.10_kernelsu.ko`（349,936 B，与 release 同尺寸）=**与本机内核同 KMI**，
   因此跳过 vermagic 是 ABI 安全的（不是猜的）。

顺序已改为 **root → KernelSU → hand-off**（hand-off 的 execve 永不返回，之前的 KSU 代码是死代码）。

## 三、为什么 bit16 只能抽签（不必再试）

被写进 `cred->cap_effective` 的**值**必须同时满足两条硬约束：

- ①它会被 `rb_erase` 当节点**解引用/写入**（`*(child)=pc`），所以必须是**已映射的内核 VA**
  （落在我们自己的 spray 页里）——小用户地址撞 PAN，跳到邻居页会写进别人家的内核内存；
- ②**这个值本身就是 cap_effective 的位图** ⇒ bit16/bit21 只能取自该地址自身的位。

用 `PSELECT_CAPS_OFF` 的进位去扭位：`V16 = p16 XOR 进位`，两种取舍都仍是 50%（推导进 skill）；
用 `PSELECT_CAPS_VALUE` 写小地址（如 `0x2100C0`，位刚好齐全）：不是内核 VA，erase 那步就崩。
⇒ **不能确定性置位，只能抽签。**

实测（LKM 开关打开后的 4 发）：`80226080c0`(16=0,21=1)、`899ea480c0`(16=0,21=1)、
`88358480c0`(0/0/0)、`8842da00c0`(0/0/0) —— bit16 **0/4**；含 14:05 的 `a42b80c0`(16=1，当时开关未开)
累计 1/5。

## 四、稳定性：设备健康同样是抽签（冻结的真正原因）

同一份二进制、同一套几何，幸存与致死都出现过：

- 幸存：14:19、14:33、15:07(#1)、15:36 等（`zyg` 保持、`uSID=0`）；
- 致死：写入落地后 ~10s `zyg 5→0`、`unknown SID` 失控（59→317 / 40s）→ framework 死 → 需复位。

**最要命的一条（新）**：致死**不需要写入成功**。15:56 那发 stage-1 连续三次未命中、coordinator
主动放弃（`AP: SELinux still enforcing after 3 worker tries`），设备照样塌。⇒ 打死设备的是
**prep 机器本身**（543 fork + 64GB mmap），不是写入落点。

单发需同时凑齐：触发命中 ≈50% × bit16 ≈50% × framework 存活 ≈50% ≈ **15%** ⇒ 期望 ~7 发、
45–60 分钟、4–6 次死机。**这是抽奖而不是工程问题**，故冻结。

## 五、复位与节奏机制（实测，别再踩）

- `adb reboot` / `toybox reboot` / `/system/bin/reboot` **全部无效**（非 root 没有 CAP_SYS_BOOT）；
  **唯一有效的软重启 = `adb shell 'svc power reboot'`**，且它在 framework 将死时仍有效
  ⇒ 先自救，救不动再长按电源键 10–15s。
- **每次重启必须用 `boot_id` 变化验证**。否则你以为在「1 发/boot」，实际在同一 boot 上连打；
  4 套 park 机器 + load 175 → `BUG: workqueue lockup … stuck for 31s!/37s!` → 死机。
- 防死循环 harness：`oppo-2/safeloop3.sh`（75s 无日志增长且设备无 exploit 进程 ⇒ 弃发；
  `ps -A|grep -c zygote` 掉即软重启；每发一个 boot + bootid 校验）。
- 提权后的 fs view：**`/data/local/tmp` 写 = EPERM，但 `/dev` 可写、`/proc` 可读**。⇒ 后续阶段要用的
  文件必须在写入前用 fd 预开、用 `execveat(fd,"",…,AT_EMPTY_PATH)` 拉起；诊断写 `/dev`；
  `/dev/kmsg` 单次 read 返回**最老**记录，要排空 ring 再取最新。
